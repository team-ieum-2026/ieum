# 매칭 평가 정답표, 라벨링 방법

매칭 추천의 Top-3(수료생마다 추천하는 상위 3개 공고 카드)를 채점할 때 쓰는 정답표를 어떻게 만들었는지 정리한다.

판정 규칙의 코드는 `rubric.py` 하나다. 이 문서와 코드가 다르면 코드를 기준으로 하고 이 문서를 고친다.

> 매칭 담당(AI-B)은 최종 평가 전까지 아래 파일을 열지 않는다. 정답을 보고 튜닝하면 점수를 믿을 수 없다.
> - `gold/`: 정답표
> - `postings/spec.json`: 공고마다 대상 수료생, 정답과 함정 구분, 함정 유형을 적은 명세. 사실상 정답표다.
> - `review/*_test.*`: test 검수 시트, 답안, 규칙 판정. 시트만 봐도 어떤 쌍이 2점 후보인지 드러난다.
>
> AI-B는 `review/*_dev.*`만 검수한다. dev 규칙 판정(`sample_key_dev.csv`)은 자기 채점을 마친 뒤에 연다.
>
> 공개해도 되는 파일: `postings/out/eval_postings.json`(라벨 없는 공고 본문), `split.json`(dev와 test 명단), `rubric.py`(판정 규칙), 이 문서.

## 1. 판정 기준

수료생 한 명과 공고 하나를 놓고 판정한다.

| 점수 | 뜻 |
| --- | --- |
| 2 | 적합 |
| 1 | 부분 적합 |
| 0 | 부적합 |

2점은 다섯 조건이 모두 맞을 때 준다. 다섯 조건은 직무, 경력, 학력, 희망 지역, 필수 기술이다. 필수 기술은 모두 갖춰야 한다.

1점은 직무가 맞고 나머지 네 조건 중 하나만 부족할 때 준다. 부족한 것이 기술이면, 필수 기술을 절반 이상 갖춰야 1점이다.

0점은 그 밖의 경우다. 직무가 다르거나, 두 조건 이상이 부족하거나, 필수 기술이 절반보다 적으면 0점이다.

### 조건별 규칙

- 직무: 수료생의 희망 직무를 직무군으로 묶어 비교한다. 직무군은 백엔드, 프론트엔드, 풀스택, AI 서비스, 데이터, 클라우드 인프라, 게임, 임베디드다. 풀스택 수료생은 풀스택 공고만 직무가 맞는 것으로 본다.
- 경력: 공고의 경력 칸이 `경력`이면 조건에 맞지 않는다. `신입`과 `관계없음`은 맞는다.
- 학력: 학력무관, 고졸, 대졸(2~3년), 대졸(4년), 석사, 박사 순으로 높다. 공고의 요구가 수료생의 최종 학력보다 높으면 맞지 않는다.
- 지역: 공고 근무지의 시도(서울, 경기, 인천)가 수료생의 희망 지역에 있어야 한다.
- 필수 기술: 공고 자격요건에 적힌 기술이다. 우대 조건은 판정에 넣지 않는다.

수료생의 기술은 `skills` 칸만 본다. 자기소개서와 README 본문은 보지 않는다. 평가용 수료생은 `skills`의 기술이 모두 프로젝트 자료에 나오는지 검사했다(`personas/check_students.py`). 생성 공고 기준으로 "본문에는 있는데 `skills`에 없어서 기술이 부족해진 쌍"은 0건이다.

### 동의어

동의어는 한 방향만 인정한다. 공고가 넓은 표기를 쓰고 수료생이 그 안의 구체 기술을 가지면 인정한다. 반대 방향은 인정하지 않는다.

예를 들어 공고가 "Spring"이고 수료생이 Spring Boot를 가지면 인정한다. 공고가 "Spring Boot"이고 수료생이 Spring만 가지면 인정하지 않는다.

| 공고 표기 | 인정하는 수료생 기술 |
| --- | --- |
| Spring, 스프링 | Spring Boot |
| SQL, RDBMS | MySQL, PostgreSQL |
| LLM API | Gemini API, OpenAI API |
| JavaScript | TypeScript, React, Vue.js, Next.js, Node.js |
| HTML/CSS | React, Vue.js, Next.js |
| C/C++ | C |

### 맞는 공고가 없는 수료생

10번(게임 클라이언트), 13번(부산 희망), 17번(경기 임베디드)은 공고 풀에 적합한 공고가 없다. 세 명은 점수와 별도로 본다. 적합(2점)이 아닌 카드가 1장이라도 추천되면 실패다. 추천이 비어 있거나 3장보다 적은 것이 정답이다.

10번과 13번은 적합한 공고가 없도록 설계했다. 17번은 교차 라벨 결과 적합한 공고가 없고 부분 적합(1점)만 있다. 생성 공고 900276번(경력 부족)과 실제 공고 616번(리눅스 경험 부족)이다. 부분 적합 공고를 추천해도 실패로 본다.

### 루브릭 동결

루브릭(판정 기준)은 매칭 모델의 결과를 보기 전에만 바꾼다. 결과를 본 뒤에 바꾸면 결과에 맞춰 채점하는 셈이다.

지금까지의 변경(7장)은 모두 정답표 분포와 사람 검수만 보고 했다. 평가 결과 파일에는 채점에 쓴 `rubric.py`의 커밋 해시를 함께 남긴다.

## 2. 라벨 파일

정답표는 두 파일로 나눈다. 한 수료생을 위한 함정이 다른 수료생에게는 정답일 수 있기 때문이다. 예를 들어 10번(게임)을 위한 함정 "게임 플랫폼 웹 백엔드(Unity 우대)"는 백엔드 수료생에게는 적합한 공고다.

| 파일 | 답하는 질문 | 범위 | 쓰는 곳 |
| --- | --- | --- | --- |
| `gold/gold_matching.csv` | 이 공고를 왜 만들었나 | 정답과 함정 공고 91건, 대상 수료생 | 설계 의도별(함정 유형, 난이도)로 결과를 나눠 볼 때 |
| `gold/pair_labels.csv` | 이 공고가 이 수료생에게 실제로 맞나 | 수료생 20명과 공고 전체의 쌍 | 채점 |

`pair_labels.csv`의 칸은 다음과 같다.

- `score`: 2, 1, 0
- `violations`: 어긋난 조건. `JOB`(직무), `CAREER`(경력), `EDU`(학력), `REGION`(지역), `SKILL`(기술)
- `origin`: 판정의 출처. `TARGET`은 그 수료생을 위해 만든 공고, `RULE`은 다른 수료생을 위한 공고를 규칙으로 판정한 것이다. 실제 공고와 일반 공고의 판정 결과는 나중에 추가한다.
- `target_label`, `trap_type`: 그 공고를 만든 목적

## 3. 개발 평가와 최종 평가 분리

공고 풀만 다르게 해서는 분리가 되지 않는다. 개발 중 평가에 쓴 (수료생, 공고) 쌍이 최종 평가에 그대로 다시 나오기 때문이다. 그래서 수료생을 나눈다. 명단은 `split.json`에 있고, 결과를 보기 전에 확정했다.

| | 수료생 | 볼 수 있는 것 | 실행 |
| --- | --- | --- | --- |
| dev | 1, 2, 3, 5, 8, 13, 14, 15 (8명) | 점수, 추천 카드별 점수와 어긋난 조건 | 자유롭게 |
| test | 4, 6, 7, 9, 10, 11, 12, 16, 17, 18, 19, 20 (12명) | 전체 점수만 | 최종 전 1~2회 |

dev는 개발 중 튜닝에 쓰는 수료생이고, test는 최종 평가에만 쓰는 수료생이다.

- 1번은 시연 주인공이라 결과를 어차피 계속 보게 된다. 그래서 dev에 두었다.
- 맞는 공고가 없는 수료생 3명은 dev 1명(13번), test 2명(10번, 17번)으로 나눴다(10/29 팀 합의). 함정 유형 5가지와 정답 난이도 A, B, C는 양쪽에 모두 있다.
- 드문 직무와 자료가 부실한 수료생은 test에 더 많이 두었다. 서비스 가치가 드러나는 곳이라 처음 보는 상태로 재야 한다.
- 대가도 있다. test 카드가 36장이라 Precision@3(추천 카드 중 적합 카드의 비율)의 신뢰구간이 ±15%p 안팎으로 넓다. 발표에서는 test 점수를 구간과 함께 보고하고, dev 점수는 "튜닝에 쓴 수료생"이라고 밝힌다.

## 4. 만든 방법

### 정답과 함정 공고 91건 (완료)

1. 명세표(`postings/spec.json`)에 공고마다 직무군, 경력, 학력, 지역, 필수 기술을 구조화된 칸으로 적었다.
2. 정답은 대상 수료생에게 다섯 조건이 모두 맞게 설계했다. 함정은 지정한 조건 하나만 어긋나게 설계했다. 함정은 경력 12건, 기술 9건, 직무 8건, 지역 6건, 학력 5건이다.
3. 정답 난이도는 세 가지다. A는 쉬운 공고, B는 도메인이 다른 공고다. C는 필수 기술을 모두 갖췄지만 공고에 다른 표현으로 적은 공고다. 예: "벡터 데이터베이스", "SQL 매퍼 프레임워크".
4. 본문은 LLM(대규모 언어 모델)이 아니라 `render_postings.py`가 명세의 칸으로 틀에 맞춰 만들었다. 일반 공고의 문체 5가지를 쓴다.
5. `check_postings.py`가 세 가지를 검사한다.
   - 정답과 함정이 설계대로인지 (루브릭)
   - 본문에서 조건을 다시 뽑았을 때 명세와 같은지. 경력 연수, 학력 문구, 필수 기술 목록, 경력과 학력과 지역 칸을 비교한다.
   - 수료생 자료와 겹치는 구절이 없는지 (정답 누출)
6. `cross_label.py`가 명세표의 칸으로 20명과 91건의 모든 쌍을 루브릭으로 판정해 `pair_labels.csv`를 만든다.

두 번째 검사가 필요한 이유가 있다. 라벨은 명세로 매기지만 모델은 본문을 읽는다. 둘이 다르면 라벨이 틀린 채로 채점된다. 다르면 본문을 명세에 맞게 고친다.

### 실제 공고 138건, 일반 공고 150건 (예정, 11/2 전 완료)

담당은 AI-A다. 정답표를 만든 방식을 가장 잘 알아서 빨리 끝낼 수 있다.

명세표가 없어서 본문에서 조건을 뽑아야 한다. 판정은 생성 공고와 같은 `rubric.py`로 해서 공고 출처에 따라 기준이 달라지지 않게 한다.

라벨은 추천에 나온 카드만이 아니라 20명과 288건의 모든 쌍에 매긴다. 추천 결과를 보고 고른 쌍만 라벨링하면 결과를 보고 정답을 정하는 셈이 된다. test 실행 결과는 라벨링이 끝날 때까지 열지 않는다.

1. 정형 칸(직종, 경력, 학력, 지역)으로 명백한 0점을 먼저 거른다. 칸이 채워진 경우에만 거르고, 비어 있으면 다음 단계로 넘긴다.
2. 남은 공고는 Gemini가 본문에서 다섯 조건을 추출한다. 본문 인용을 함께 JSON(구조화된 데이터 형식)으로 받는다. 점수는 묻지 않는다.
3. 추출 결과를 `rubric.py`에 넣어 판정한다.
4. 2점 쌍과 층화 표본을 사람이 검수해 확정한다.

매칭 순위는 Gemini가 아니라 리랭커(후보를 다시 정렬하는 모델, bge-reranker)가 정한다. 그래서 라벨 추출에 Gemini를 써도, 같은 모델이 같은 곳에서 함께 틀리는 문제는 크지 않다.

## 5. 검수

`review/make_sample.py`로 검수 시트를 만든다. 검수자는 규칙 판정을 가린 채 공고 본문을 보고 채점한다. 명세표는 보여 주지 않는다.

검수는 dev와 test로 나눈다(10/29 결정).

| 묶음 | 쌍 | 검수자 | 파일 |
| --- | --- | --- | --- |
| dev (8명) | 35 | AI-B | `review/*_dev.*` |
| test (12명) | 48 | AI-A | `review/*_test.*` |

dev와 test를 각자 1명이 검수한다. 일정상 검수자를 2명씩 둘 시간이 없기 때문이다.

test 검수자(AI-A)는 매칭을 개발하지 않았다. 다만 정답과 함정 공고를 직접 설계했다. 그래서 검수할 때 명세표와 규칙 판정을 열지 않고, 공고 본문과 수료생 자료만 보고 채점한다.

매칭 담당(AI-B)이 test 쌍을 보면 test 수료생의 정답을 알게 된다. 그러면 최종 평가가 처음 보는 상태가 아니게 된다. dev는 원래 결과를 보며 튜닝하는 쪽이라 AI-B가 봐도 된다.

표본은 83쌍이다(dev 35쌍, test 48쌍).

- 규칙이 다른 수료생 쌍에 준 2점은 모두 넣었다(65쌍). 정밀도 채점을 직접 좌우하기 때문이다.
- 1점과 0점은 어긋난 조건별로 4쌍씩 넣었다. 2점을 놓친 판정이 없는지(재현율) 보기 위해서다.
- 대상 정답과 함정은 `check_postings.py`가 이미 검사하므로 넣지 않았다.

### 절차

dev와 test를 따로 집계한다(`review/compare_sample.py dev` 또는 `test`).

1. 검수자는 규칙 판정을 보지 않고 채점한다. 규칙 판정(`sample_key_*.csv`)은 채점을 마친 뒤에 연다.
2. 사람의 판정을 규칙과 비교한다. 2점 정밀도(규칙이 2점을 준 쌍 중 사람도 2점을 준 비율)와 2점 재현율(사람이 2점을 준 쌍 중 규칙도 2점을 준 비율)을 신뢰구간과 함께 낸다.
3. 2점 정밀도의 95% 구간 하한이 85% 이상이면 규칙 판정을 믿고 쓴다. 낮으면 틀린 패턴을 보고 규칙을 고친다. 고치는 것은 루브릭 동결 전에만 한다.
4. 규칙과 갈린 쌍은 원문을 다시 보고 결론을 해석 사례집에 남긴다. 채점 실수인지, 루브릭 문구가 모호한지 구분한다.

### 해석 사례집

규칙과 달랐던 사례의 결론을 적는다. 실제 공고를 판정할 때 그대로 기준이 된다.

| 사례 | 결론 | 근거 |
| --- | --- | --- |
| 공고 도메인(결제, AI 등) 경험이 없는 수료생 (dev 21, 33번) | 점수를 깎지 않는다 | 루브릭은 직무군만 본다. 도메인 경험은 판정 조건이 아니다 |
| 공고 "OpenAI API", 수료생 "Gemini API" (dev 25번) | 인정하지 않는다 (1점, 기술 부족) | 동의어는 넓은 표기에서 구체 기술로만 인정한다. "LLM API"라면 둘 다 인정하지만, 서로 다른 구체 기술끼리는 같은 기술로 보지 않는다 |
| 13번 수료생(부산 희망)에게 서울, 경기 공고 (dev 16, 31번) | 지역 부족 (1점) | 채점 때 희망 지역을 놓친 실수였다. 수료생의 희망 지역을 먼저 확인한다 |

## 6. 한계

- 규칙은 도메인과 업무 수준을 보지 않는다. 예를 들어 "리딩", "설계" 같은 업무 수준은 경력 칸이 `경력`일 때만 잡힌다.
- 직무군이 거칠다. 같은 백엔드라도 SI(시스템 통합) 유지보수와 서비스 개발을 구분하지 않는다.
- 생성 공고는 기술 요구가 칸으로 정리돼 있어 판정이 명확하다. 실제 공고에는 "C/Python"처럼 해석이 갈리는 표현이 있다.
- 검수 표본 밖의 `origin = RULE` 쌍은 사람이 보지 않았다. 규칙이 2점을 준 쌍은 모두 검수했다.
- dev와 test 모두 검수자가 1명이라 사람끼리의 일치도를 내지 못한다. 사람의 판정이 얼마나 흔들리는지는 보이지 못하고, 규칙과 갈린 쌍을 해석 사례집으로 확인한다.
- test 검수자(AI-A)는 정답과 함정 공고를 설계한 사람이다. 명세표를 보지 않고 채점해도, 설계 의도를 기억해 규칙과 비슷하게 판정할 수 있다. 그래서 test의 2점 정밀도는 실제보다 높게 나올 수 있다.
- `gold/`와 `spec.json`은 같은 저장소에 있어서 기술적으로 막을 수 없다. 열지 않는 것은 약속이다.
