# 매칭 평가 정답표 — 라벨링 방법

매칭 추천(Top-3)을 채점할 때 쓰는 정답표를 어떻게 만들었는지 정리한 문서입니다.
판정 규칙의 코드는 `rubric.py` 하나입니다. 이 문서와 코드가 다르면 코드를 기준으로 하고 이 문서를 고칩니다.

> **매칭 담당(AI-B)은 아래 파일을 최종 평가 전까지 열지 않습니다.** 정답을 보고 튜닝하면 점수를 믿을 수 없게 됩니다.
> - `gold/` (정답표)
> - `postings/spec.json` (공고마다 대상 수료생 · 정답/함정 · 함정 유형이 적힌 명세. 사실상 정답표)
> - `review/*_test.*` (test 검수 시트 · 답안 · 규칙 판정. 시트에도 어떤 쌍이 2점 후보인지 드러남)
>
> AI-B는 `review/*_dev.*` 만 검수합니다. dev 규칙 판정(`sample_key_dev.csv`)은 자기 채점을 마친 뒤 엽니다.
>
> 공개해도 되는 것: `postings/out/eval_postings.json`(공고 본문, 라벨 없음), `split.json`(dev/test 명단), `rubric.py`(판정 규칙), 이 문서.

## 1. 판정 기준 (루브릭)

수료생 한 명과 공고 하나를 놓고 판정합니다.

| 점수 | 기준 |
| --- | --- |
| **2 적합** | 다섯 가지가 모두 맞음: ① 직무 일치 ② 경력 조건(신입 · 관계없음) ③ 학력 조건 ④ 희망 지역 안 ⑤ **필수 기술을 모두 갖춤** |
| **1 부분** | 직무는 맞고 ②~⑤ 중 **한 가지만** 부족. 기술이 부족한 경우는 필수 기술을 절반 이상은 갖춰야 부분 |
| **0 부적합** | 그 외 (직무가 다름, 두 가지 이상 부족, 필수 기술이 절반 미만) |

세부 규칙
- **직무**: 수료생 희망 직무를 직무군으로 묶어 비교 (백엔드 · 프론트엔드 · 풀스택 · AI 서비스 · 데이터 · 클라우드 인프라 · 게임 · 임베디드). 풀스택 수료생은 풀스택 공고만 직무 일치.
- **경력**: 공고 경력 칸이 `경력`이면 불충족. `신입` · `관계없음`은 충족.
- **학력**: `학력무관 < 고졸 < 대졸(2~3년) < 대졸(4년) < 석사 < 박사`. 공고 요구가 수료생 최종 학력보다 높으면 불충족.
- **지역**: 공고 근무지의 시 · 도(서울 · 경기 · 인천)가 수료생 희망 지역에 있어야 함.
- **필수 기술**: 공고 자격요건에 적힌 기술. **우대 조건은 판정에 넣지 않음.**
- **수료생 기술의 기준**: 수료생의 `skills` 칸만 봅니다. 자기소개서 · README 본문은 보지 않습니다. 평가용 수료생은 `skills` 의 기술이 모두 프로젝트 자료에 나오도록 검사했고(`personas/check_students.py`), 생성 공고 기준으로 "본문에는 있는데 `skills` 에 없어서 기술 부족이 된 쌍"은 0건입니다.
- **동의어는 한 방향만 인정**: 공고가 넓은 표기를 쓰고 수료생이 그 안의 구체 기술을 가지면 인정합니다. 반대는 인정하지 않습니다.

  | 공고 표기 | 인정하는 수료생 기술 |
  | --- | --- |
  | Spring · 스프링 | Spring Boot |
  | SQL · RDBMS | MySQL · PostgreSQL |
  | LLM API | Gemini API · OpenAI API |
  | JavaScript | TypeScript · React · Vue.js · Next.js · Node.js |
  | HTML/CSS | React · Vue.js · Next.js |
  | C/C++ | C |

  예: 공고 "Spring" ← 수료생 Spring Boot → 인정. 공고 "Spring Boot" ← 수료생 Spring → 불인정.

### 맞는 공고가 없는 수료생
10번(게임 클라이언트) · 13번(부산 희망)은 풀에 적합한 공고가 없도록 설계했습니다. 이 두 명은 위 점수와 별도로 **적합(2점)이 아닌 카드가 1장이라도 추천되면 실패**로 봅니다. 추천이 비어 있거나 3장보다 적은 것이 정답입니다.
17번(경기 임베디드)은 실제 공고에 부분 적합 공고(616번, 리눅스 경험 부족)가 있어, 교차 라벨이 끝난 뒤 "맞는 공고 있음 / 없음"을 확정합니다.

### 루브릭 동결
- 루브릭은 **매칭 모델 결과를 보기 전에만** 바꿉니다. 결과를 본 뒤에 바꾸면 결과에 맞춰 채점하는 셈입니다.
- 지금까지의 변경(6장)은 모두 정답표 분포와 사람 검수만 보고 했습니다.
- 평가 결과 파일에는 채점에 쓴 `rubric.py` 의 **커밋 해시**를 함께 기록합니다.

## 2. 라벨 파일

| 파일 | 질문 | 범위 | 쓰는 곳 |
| --- | --- | --- | --- |
| `gold/gold_matching.csv` | 이 공고를 **왜 만들었나** | 정답 · 함정 공고 91건 × 대상 수료생 | 결과를 설계 의도별(함정 유형 · 난이도)로 나눠 볼 때 |
| `gold/pair_labels.csv` | 이 공고가 이 수료생에게 **실제로 맞나** | 수료생 20명 × 공고 전체 쌍 | **채점** |

두 파일을 나눈 이유: 한 수료생을 위한 함정이 다른 수료생에게는 정답일 수 있습니다. 예를 들어 10번(게임)용 함정 "게임 플랫폼 웹 백엔드(Unity 우대)"는 백엔드 수료생에게는 적합한 공고입니다.

`pair_labels.csv` 칸
- `score`: 2 · 1 · 0
- `violations`: 어긋난 조건 (`JOB` · `CAREER` · `EDU` · `REGION` · `SKILL`)
- `origin`: `TARGET` 그 수료생을 위해 만든 공고 / `RULE` 다른 수료생용 공고를 규칙으로 판정 / (예정) 실제 · 일반 공고 판정 결과
- `target_label` · `trap_type`: 그 공고를 만든 목적

## 3. 개발 · 최종 평가 분리

공고 풀만 달리해서는 분리가 되지 않습니다. 개발 중 평가의 (수료생, 공고) 쌍이 최종 평가에 그대로 다시 나오기 때문입니다. 그래서 **수료생을 나눕니다** (`split.json`, 결과를 보기 전에 확정).

| | 수료생 | 볼 수 있는 것 | 실행 |
| --- | --- | --- | --- |
| **dev** | 1 · 2 · 3 · 5 · 8 · 13 · 14 · 15 (8명) | 점수, 추천 카드별 점수와 어긋난 조건 | 자유롭게 |
| **test** | 4 · 6 · 7 · 9 · 10 · 11 · 12 · 16 · 17 · 18 · 19 · 20 (12명) | **전체 점수만** | 최종 전 1~2회 |

- 1번은 시연 주인공이라 결과를 어차피 계속 보게 되므로 dev에 두었습니다.
- 맞는 공고가 없는 수료생 3명은 dev 1명 · test 2명으로 나눕니다(13 dev, 10 · 17 test, 10/29 팀 합의). 함정 유형 5가지와 정답 난이도 A · B · C는 양쪽에 모두 있습니다.
- 드문 직무와 자료가 부실한 수료생은 test에 더 많이 두었습니다. 서비스 가치가 드러나는 곳이라 처음 보는 상태로 재야 합니다.
- 대가: test 카드가 36장이라 Precision@3 신뢰구간이 ±15%p 안팎으로 넓습니다. 발표에서는 test 점수를 구간과 함께 보고하고, dev 점수는 "튜닝에 쓴 수료생"이라고 밝힙니다.

## 4. 만든 방법

### 정답 · 함정 공고 91건 (완료)
1. 명세표(`postings/spec.json`)에 공고마다 직무군 · 경력 · 학력 · 지역 · 필수 기술을 **구조화된 칸**으로 적음.
2. 정답은 대상 수료생에게 다섯 조건이 모두 맞게, 함정은 **지정한 조건 하나만** 어긋나게 설계 (경력 12 · 기술 9 · 직무 다름 8 · 지역 6 · 학력 5).
3. 정답 난이도: A 쉬움 · B 도메인이 다름 · C 필수 기술은 모두 갖췄지만 공고에 **다른 표현**으로 적음 (예: "벡터 데이터베이스", "SQL 매퍼 프레임워크").
4. 본문은 LLM이 아니라 `render_postings.py`가 명세의 칸으로 **틀에 맞춰** 만듦 (일반 공고의 문체 5가지).
5. `check_postings.py`가 검사:
   - 정답 · 함정이 설계대로인지 (루브릭)
   - **본문에서 조건을 다시 뽑아 명세와 같은지** (경력 연수 · 학력 문구 · 필수 기술 목록 · 경력/학력/지역 칸). 라벨은 명세로 매기지만 모델은 본문을 읽으므로, 둘이 다르면 라벨이 틀린 채로 채점됩니다. 다르면 **본문을 명세에 맞게** 고칩니다.
   - 수료생 자료와 겹치는 구절이 없는지 (누출)
6. `cross_label.py`가 명세표의 칸으로 **20명 × 91건 전체 쌍**을 루브릭 판정 → `pair_labels.csv`.

### 실제 138건 · 일반 150건 (예정)
명세표가 없어 본문에서 조건을 뽑아야 합니다. **판정은 생성 공고와 같은 `rubric.py`로** 해서, 공고 출처에 따라 기준이 달라지지 않게 합니다.
1. 정형 칸(직종 · 경력 · 학력 · 지역)으로 명백한 0점을 먼저 거름. **칸이 채워진 경우에만** 거르고, 비어 있으면 다음 단계로 넘김.
2. 남은 공고는 Gemini가 본문에서 다섯 조건을 **본문 인용과 함께 JSON으로 추출만** 함. 점수는 묻지 않음.
3. 추출 결과를 `rubric.py`에 넣어 판정.
4. 2점 쌍과 층화 표본을 사람이 검수해 확정.

참고: 매칭 순위는 Gemini가 아니라 리랭커(bge-reranker)가 정하므로, 라벨 추출에 Gemini를 써도 같은 모델이 같은 곳에서 같이 틀리는 문제는 크지 않습니다.

## 5. 검수

`review/make_sample.py`로 검수 시트를 만들고, 검수자가 **규칙 판정을 가린 채 공고 본문을 보고** 채점합니다. 검수자에게 명세표는 보여 주지 않습니다.

검수는 dev · test로 나눕니다 (10/29 결정).

| 묶음 | 쌍 | 검수자 | 파일 |
| --- | --- | --- | --- |
| dev (8명) | 35 | AI-A + AI-B | `review/*_dev.*` |
| test (12명) | 48 | AI-A + 매칭 개발을 하지 않는 사람 (FE-A · FE-B 중 1명) | `review/*_test.*` |

매칭 담당(AI-B)이 test 쌍을 보면 test 수료생의 정답을 알게 되어 최종 평가가 "처음 보는 상태"가 아니게 됩니다. dev는 원래 결과를 보며 튜닝하는 쪽이라 AI-B가 봐도 됩니다.

표본 (현재 83쌍 = dev 35 + test 48)
- 규칙이 다른 수료생 쌍에 준 **2점은 전부** (65쌍). 정밀도 채점을 직접 좌우합니다.
- 1점 · 0점은 **어긋난 조건별로 4쌍씩**. 2점을 놓친 판정이 없는지(재현율) 봅니다.
- 대상 정답 · 함정은 `check_postings.py`가 설계대로인지 이미 검사하므로 넣지 않습니다.

절차 (`review/compare_sample.py dev|test`, dev · test 따로 집계)
1. **2명이 서로 답을 보지 않고** 채점.
2. 먼저 **사람끼리 일치도(Cohen's κ)**를 봅니다. 0.8 미만이면 규칙이 아니라 루브릭 문구가 모호한 것입니다. 갈린 쌍을 아래 해석 사례집에 정리하고 다시 채점합니다.
3. 사람끼리 같은 쌍으로 규칙과 비교: **2점 정밀도**(규칙 2점 중 사람도 2점)와 **2점 재현율**(사람 2점 중 규칙도 2점)을 신뢰구간과 함께 냅니다.
4. 기준: 2점 정밀도의 95% 구간 **하한이 85% 이상**이면 규칙 판정을 믿고 씁니다. 낮으면 틀린 패턴을 보고 규칙을 고칩니다 (루브릭 동결 전에만).

## 6. 한계

- 규칙은 **도메인 · 업무 수준**(예: "리딩", "설계" 업무)을 보지 않습니다. 경력 칸이 `경력`일 때만 수준 차이를 잡습니다.
- 직무군이 거칩니다. 같은 "백엔드"라도 SI 유지보수와 서비스 개발을 구분하지 않습니다.
- 생성 공고는 기술 요구가 칸으로 정리돼 있어 판정이 명확하지만, 실제 공고는 "C/Python"처럼 해석이 갈리는 표현이 있습니다.
- 검수 표본 밖의 `origin = RULE` 쌍은 사람이 보지 않았습니다 (규칙 2점은 전수 검수).
- `gold/`, `spec.json` 은 같은 저장소에 있어 기술적으로 막을 수 없습니다. 열지 않는 것은 약속입니다.
