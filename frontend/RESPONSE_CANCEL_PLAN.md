# 지원·PASS·도움 요청 응답 취소 기획 및 API 요청 명세

작성: 2026-11-01. 대상: 수료생 M1 맞춤 공고, M2 공고 상세.

이번 승인 범위는 **프론트엔드와 API 요청 명세 준비**다. 기존 `POST .../response` 계약은 유지한다. 아래 DELETE는 신규 제안이며, 백엔드·DB·기존 공용 API 문서는 수정하지 않았다. 실제 서버에는 취소 API가 아직 없어 실제 응답 취소는 동작하지 않는다. 이 경우 오류를 표시하고 기존 응답을 유지한다.

## 화면 동작

- 응답이 `APPLY`(화면: 지원완료/지원함), `PASS`, `HELP`일 때 상태 배지 옆 또는 공고 상세에 `취소` 버튼을 표시한다. `NONE`에는 표시하지 않는다.
- `지원 취소`, `패스 취소`, `도움 요청 취소` 확인창에서 `유지하기`를 누르거나 창을 닫으면 요청하지 않는다.
- 지원 취소 안내: 공고별 작성 중인 지원서는 삭제되고, 내 프로필에 저장한 원본 자료는 유지된다. 이미 검토를 요청한 지원서는 직접 취소할 수 없다고 안내한다.
- PASS 취소 안내: 사유와 메모를 지우고 응답 전으로 되돌린다.
- HELP 취소 안내: 도움 요청을 닫고 응답 전으로 되돌린다. 담당자가 이미 연락을 시작한 요청은 직접 취소할 수 없다고 안내한다. 취소 후 새 도움 요청이 가능하다.
- 처리 중에는 확인·닫기를 막고 `취소 중…`을 표시한다. 연속 클릭으로 중복 전송하지 않는다.
- 성공 응답을 확인한 뒤에만 `NONE`으로 표시하고 목록·지원 현황을 재조회한다. 다시 지원·PASS·도움 요청을 선택할 수 있다.
- 실패하면 상태를 바꾸지 않고 확인창에 오류와 재시도 버튼을 유지한다. 404/405/501은 취소 요청을 처리할 수 없다고 안내한다.
- 취소는 기존 공고의 응답만 되돌린다. 이미 새 추천을 받은 경우 과거 공고를 현재 추천 3장에 강제로 끼워 넣지 않는다.

## 제안 API — 백엔드 협의·구현 필요

```http
DELETE /api/recommendation-items/{itemId}/response?expectedResponse=APPLY
```

PASS는 `expectedResponse=PASS`, 도움 요청은 `expectedResponse=HELP`. 요청 본문은 없다. `studentId`는 프론트엔드의 ID별 모의 데이터 구분에만 쓰고, 이 DELETE 요청에 추가하지 않는다. 실제 서비스의 소유권 확인은 기존 수료생 식별 정책에 맞춰 백엔드에서 수행해야 한다.

성공: HTTP 200, 기존 공통 JSON envelope를 유지한다. `applicationId`는 생략하지 않고 null이다. 204는 현재 FE 공통 클라이언트가 JSON을 요구하므로 사용하지 않는다.

```json
{ "data": { "itemId": 91, "response": "NONE", "applicationId": null } }
```

실패 예시:

```json
{ "error": { "code": "INVALID_STATUS", "message": "이미 검토를 요청한 지원서는 직접 취소할 수 없어요. 담당자에게 문의해주세요." } }
```

| 조건 | HTTP / 코드 | 처리 |
| --- | --- | --- |
| 항목 없음 | 404 / RECOMMENDATION_ITEM_NOT_FOUND | 상태 유지 |
| 잘못된 expectedResponse | 400 / INVALID_REQUEST | APPLY·PASS·HELP만 허용 |
| 요청 당시와 다른 응답 | 409 / INVALID_STATUS | 다른 응답을 지우지 않음, 재조회 안내 |
| 연락을 시작했거나 이미 종료된 도움 요청 | 409 / INVALID_STATUS | 기존 요청 유지, 담당자 문의 |
| 검토 요청 이후 지원서 | 409 / INVALID_STATUS | 기존 지원서 유지, 담당자 문의 |
| 이미 NONE | 200 / NONE | 멱등 처리, 지원서를 새로 만들지 않음 |
| 통신·서버 실패 | 기존 오류 규칙 | 롤백, 재시도 가능 |

`expectedResponse`는 다른 종류로 바뀐 응답을 실수로 취소하지 않도록 확인하기 위한 값이다. 동일 응답 유형을 취소·재응답하는 여러 탭의 오래된 요청까지 구분하려면 향후 version/respondedAt 조건이 필요하다. 현재 GET에 새 필드를 임의로 추가하지 않는다.

## 백엔드 처리 제안 — 미구현

다음 정책은 백엔드·PM 확인 후 구현한다. 특히 검토 요청 이후 취소가 필요하다면 담당자 검토·전달 정책을 먼저 합의해야 한다.

1. 트랜잭션에서 추천 항목과 연결된 지원서를 잠그고 현재 응답·소유권·지원서 상태를 검사한다. 동시에 지원·취소·검토 요청을 보내도 데이터가 섞이지 않도록 조건부 갱신한다.
2. PASS 취소: `response=NONE`, `pass_reason=null`, `pass_note=null`, `responded_at=null`로 되돌린다.
3. APPLY 취소: 제안 허용 상태는 `GENERATING`, `DRAFT`, `FAILED`다. `SUBMITTED`, `APPROVED`, `REJECTED`, `DELIVERED`는 409로 거절한다. 화면의 '지원완료'는 공고에 APPLY 응답했다는 뜻이며 담당자 검토 완료와 다르다.
4. 허용한 APPLY는 연결된 `application`을 삭제하고 `application_document`를 기존 FK cascade로 정리한다. 추천 항목을 NONE으로 되돌린다. 원본 프로필과 도움 요청은 변경하지 않는다. 스키마 변경은 제안하지 않는다.
5. 비동기 서류 생성이 진행 중이었다면 취소된 지원서에 결과를 저장하지 않도록 상태 조건과 트랜잭션을 검증한다. 취소 후 재지원은 새 applicationId를 발급하며, 이전 생성 작업이 새 지원서를 덮어쓰면 안 된다.
6. 지원 현황·코디네이터 집계·추천 제외 대상은 취소 후 데이터로 다시 계산한다. 취소 전 `last_response_at`을 무조건 현재 시각으로 덮어쓰지 않는다. 남아 있는 실제 응답·검토 요청·도움 요청에 근거해 무응답 판정용 시각을 재계산하는 정책이 필요하다.
7. 상태 재계산 이벤트는 취소 커밋 뒤 발행한다. 기존 지원 응답 이벤트를 재발행해 서류 생성이 시작되지 않도록 별도 취소 이벤트를 검토한다.
8. 이후 GET 상세·현재 추천·지원 현황에서 일관된 상태를 반환한다. 취소된 applicationId의 서류·진행 상태 조회는 404, 재지원 POST는 새 지원서 생성이 가능해야 한다.

HELP 추가 정책(제안): 연결된 같은 수료생·공고의 현재 도움 요청이 `OPEN`일 때만 취소한다. 트랜잭션에서 해당 요청을 잠그고 기존 `CLOSED` 상태로 변경해 이력을 남긴 후 추천 응답을 `NONE`으로 되돌린다. `CONTACTED` 또는 이미 `CLOSED`인데 추천 응답이 HELP로 남은 경우에는 409로 거절하고 상태를 재확인한다. 요청이 없으면 성공으로 위장하지 않는다. 기존에 취소한 요청이 있어도 최신 OPEN 요청을 정확히 구분해야 한다. 취소 후 코디네이터의 진행 중 요청·도움 필요 집계와 수료생 상태를 재계산한다. 기존 연락 방법·메모와 프로필·지원서는 보존한다. 취소 후 재요청 시 새 helpRequestId를 생성한다. 도움 요청 수정 PATCH와 취소가 경합할 때 취소된 요청이 다시 OPEN으로 살아나지 않도록 서버에서 조건부 처리한다. 별도 `CANCELLED` 상태나 DB 스키마는 추가하지 않는다.

## 프론트엔드 함수

| 파일 / 함수 | 역할 |
| --- | --- |
| `src/lib/api/student.ts` / `cancelItemResponse(itemId, expectedResponse, studentId)` | 실제 모드: APPLY·PASS·HELP 제안 DELETE 전송, itemId·NONE·null 성공값 검증. 목업 모드: ID별 응답 기록 정리 |
| `src/types/student.ts` / `CancellableResponse`, `ItemResponseCancelResult` | 허용 응답과 취소 결과 타입 |
| `src/components/student/ResponseCancelButton.tsx` | 조건부 버튼, 확인창, 중복 요청 방지, 로딩·오류·성공 처리 |
| `clearRememberedResponse(studentId, itemId)` | 성공 뒤 목업 세션 응답 캐시 삭제 |
| `subscribeApplicationChanges(listener)` | 목록·지원 현황·화면 복귀 시 재조회, 실제 모드에서도 성공 이벤트 통지 |

목업은 기존 저장 자료 중 이 학생·공고의 지원/PASS 기록과 성공 후 HELP 세션 응답을 정리하고 NONE 마커를 저장한다. 기본 JSON의 APPLY/PASS/HELP가 다시 살아나지 않도록 처리한다. 다른 학생·다른 공고의 자료는 유지한다. 새로 지원/PASS하면 새 응답이 NONE 마커보다 우선하며, 다시 도움을 요청하면 새 HELP 세션 응답을 표시한다. 현재 목업은 도움 요청의 OPEN/CONTACTED/CLOSED 이력을 별도로 저장하지 않으므로 서버의 연락 상태 제한은 API 응답을 가로채 검증하며, 실제 백엔드에서 강제해야 한다. 실제 모드에는 브라우저 상태만 바꿔 성공으로 보이게 하는 우회 처리가 없다.

## 검증 및 인계

- FE 검증: APPLY/PASS/HELP에 버튼 표시·NONE에는 숨김, 확인 취소 시 무요청, DELETE URL·메서드·무본문, 중복 클릭 방지, 200 뒤 NONE 복원, 409/405/통신 실패 시 기존 상태 유지, 카드 링크와 취소 버튼 분리, 화면 재조회, 반응형 표시.
- 목업 검증: 학생별 격리, 취소 후 재진입·재지원, 보호 상태 지원서 거절.
- 백엔드 구현 후 필수 통합 검증: 생성 도중 취소, 재지원, 검토 요청과 취소의 경합, 여러 탭, 취소 지원서 직접 URL, 집계·추천 제외·무응답 판정 재계산.
- HELP 추가 통합 검증: OPEN 취소, CONTACTED/CLOSED 거절, 취소 후 새 요청, 요청 수정 PATCH와 취소의 경합, 담당자 집계·상태 재계산.
- 실제 DB를 변경하는 검증은 이번 범위에서 하지 않는다. FE 성공 흐름은 브라우저에서 API 응답을 가로채 검증한다.

완료 범위: FE와 요청 명세. 미완료 범위: 실제 DELETE 서버 구현·공용 API 계약 확정·백엔드 통합 검증.
